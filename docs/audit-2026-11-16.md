# Audit ProcureAI — 16 November 2026

Catatan: dokumen ini merekam kondisi saat audit. Status perbaikan berikutnya ada di [laporan remediasi](remediation-2026-11-16.md).

Audit berdasarkan kode workspace saat ini, termasuk perubahan pada percakapan ini. Tidak mengubah logika produksi pada tahap audit. Meninjau API, auth, worker, pencarian, lokasi, crawler, ekstraksi, ranking, database, quotation, ekspor, dan JavaScript frontend.

**Kesimpulan:** aplikasi belum layak diperlakukan sebagai sumber keputusan purchasing tanpa pemeriksaan manusia. Kegagalan terpenting adalah produk yang bisa tercipta dari permintaan pengguna tanpa bukti halaman, produk beda merek tergabung, akses job yang tidak konsisten, dan penyisipan JavaScript pada tombol salin kontak.

## Bukti dan batas pemeriksaan

- Lima probe Rust berhasil mereproduksi perilaku yang salah di database SQLite in-memory dan router lokal. Sumber disimpan di `docs/audit-probes.rs`; probe sengaja menguji *perilaku bermasalah saat ini*, sehingga hasil `ok` bukan berarti implementasinya benar.
- Probe JavaScript di VM terisolasi membuktikan injeksi melalui inline handler salin kontak setelah decoding entity HTML. Tidak mengakses akun atau server lain.
- Test suite normal berjumlah 15 tes pada keadaan sebelum audit. Cakupannya belum memeriksa sejumlah skenario di bawah.
- Tidak menguji tampilan di browser, kualitas hasil pencarian internet secara langsung, performa beban, maupun eksploitasi jaringan crawler. Temuan jaringan di bawah berasal dari urutan eksekusi kode.

## Prioritas 0 — akses dan eksekusi kode

### A01. Stored XSS pada tombol salin kontak — terbukti dengan probe VM

`frontend/js/app.js:1262` dan `:1269` memasukkan nilai email/telepon ke string JavaScript di atribut `onclick`. `escapeHtml` mengganti apostrof menjadi entity, lalu `.replace(/'/g, ...)` tidak lagi menemukannya. Browser mendecode entity saat membaca handler sehingga string JavaScript dapat terputus. API edit supplier juga menerima kontak tanpa validasi format.

Dampak: nilai kontak yang sengaja disusun dapat menjalankan JavaScript ketika tombol Salin ditekan. Token autentikasi disimpan di localStorage oleh frontend sehingga dampaknya mencakup sesi pengguna.

Perbaikan: buat elemen dengan DOM API, gunakan `textContent` dan `addEventListener`; jangan menanam data sebagai kode inline. Validasi kontak tetap diperlukan.

### A02. Pengguna lain dapat membaca dan menghentikan job — terbukti dengan router lokal

`src/api/search_jobs.rs:122`, `:182`, `:236`, `:258`, `:280`, `:337` menerima pengguna terautentikasi tetapi tidak memeriksa pemilik job. Probe akun B mendapatkan HTTP 200 untuk membaca dan menghentikan job akun A. Endpoint purchasing sudah memeriksa pemilik, sehingga kebijakan akses berbeda antarfitur.

Dampak: permintaan internal, hasil, ekspor, dan aktivitas job dapat diakses oleh pengguna yang mengetahui ID; pekerjaan orang lain bisa dihentikan.

Perbaikan: pemeriksaan owner/admin bersama untuk semua endpoint job, atau definisikan akses tim yang eksplisit dan konsisten.

### A03. Pemeriksaan redirect crawler terlambat — analisis kode

`src/services/crawler.rs:36` mengikuti redirect sebelum `validate_url_safety` pada URL final di `:63`. Pada saat final URL diperiksa, permintaan sudah terkirim. Redirect perantara tidak dicek. `src/utils/url_safety.rs:96` juga mengabaikan kegagalan DNS, DNS validasi tidak dipin ke koneksi, dan IPv4-mapped IPv6 belum diperiksa sebagai IPv4 privat.

Dampak: perlindungan SSRF belum lengkap. Validasi URL awal saja tidak menjamin semua tujuan koneksi aman.

Perbaikan: validasi setiap hop sebelum request, resolusi IP yang terikat ke koneksi, dan cakupan IPv6 yang lengkap. Uji dengan server simulasi terkontrol.

### A04. Secret dan kredensial bootstrap memiliki default tetap — kondisi terlihat di kode

`src/config.rs:110` dan `src/database/mod.rs:44` memberikan nilai bawaan yang tetap ketika environment tidak diset. Tidak ada penolakan startup produksi tanpa konfigurasi aman. Ini temuan konfigurasi bersyarat; audit tidak menyatakan server yang sedang digunakan pasti memakai default.

Perbaikan: fail startup pada konfigurasi produksi yang tidak lengkap dan wajibkan kredensial bootstrap yang dipilih administrator.

## Prioritas 1 — akurasi dan integritas

### A05. Fallback membuat produk dari permintaan, bukan dari temuan — terbukti

`src/services/gemini.rs:951` selalu membentuk offer menggunakan nama barang, merek, dan part number dari request, sekalipun halaman hanya menjual kertas kantor. Probe permintaan bearing SKF 6205 terhadap halaman kertas menghasilkan offer SKF 6205; `stored_search::matches_product` kemudian menerimanya sebagai barang cocok.

Dampak: hasil palsu bisa tersimpan lalu muncul lagi pada pencarian berikutnya. Filter pencocokan baru tidak cukup jika data sumbernya sudah salah.

Perbaikan: fallback hanya membentuk offer jika ada bukti produk pada halaman; simpan yang tidak terbukti sebagai kandidat perusahaan tanpa klaim produk. Data lama perlu ditandai/ditinjau ulang.

### A06. Nomor part sama mencampur merek berbeda — terbukti

`src/database/repositories/products.rs:12` mencari produk hanya berdasarkan `part_number`; fallback berdasarkan nama juga tidak mempertimbangkan brand. Probe SKF 6205 dan NSK 6205 menghasilkan ID produk yang sama, dengan merek tetap SKF.

Dampak: penawaran supplier dapat terhubung ke merek yang salah, lalu tersaring secara salah pada pencarian lain.

Perbaikan: identitas produk gabungan merek + nomor part/model dengan normalisasi; tangani merek yang belum diketahui secara eksplisit. Perlu pemeriksaan ulang relasi yang telanjur tercampur.

### A07. Skor tinggi tanpa bukti produk — terbukti

`src/services/ranking.rs:88`, `:118`, `:141`, `:245` memberi poin karena informasi tidak diminta, nama tidak cocok, dan lokasi cocok. Probe supplier tanpa product/offer/evidence mendapat 77 poin untuk query valve pada kondisi yang diuji.

Dampak: persentase “kecocokan” terlihat meyakinkan meskipun barang belum terbukti dijual.

Perbaikan: syarat minimum bukti produk sebelum ranking relevansi; pisahkan skor lokasi dan kelengkapan, dan jangan menampilkan skor sebagai probabilitas kecocokan.

### A08. Pencocokan spesifikasi tidak membandingkan nilai/satuan — analisis kode

`src/services/ranking.rs:100` menggunakan `val.get(required)` terhadap kalimat syarat pengguna. Syarat “diameter 25mm” tidak sama dengan key JSON `inner_diameter_mm`. Sebaliknya keberadaan key dengan nilai nonkosong bisa mendapat poin tanpa mengecek nilai yang diminta.

Perbaikan: struktur atribut berisi nama, operator, nilai, dan satuan; normalisasi unit, kemudian bandingkan nilai.

### A09. Bukti ekstraksi tidak terikat ke offer dan klaim masih bisa tanpa bukti — analisis kode

`src/services/gemini.rs:666` hanya membuang kutipan yang tidak ditemukan, tetapi nilai produk/kontak/harga yang kehilangan bukti tetap dipertahankan. `src/workers/discovery.rs:817` menyimpan seluruh evidence dengan `offer_id = None`. Bukti harga produk A dapat ikut meningkatkan kelengkapan produk B karena ranking memakai evidence supplier secara keseluruhan.

Perbaikan: relasi evidence per field dan offer, lalu kosongkan/tandai klaim yang tidak didukung. Kutipan yang muncul belum tentu mendukung makna klaim.

### A10. Verifikasi dapat menyasar bukti vendor lain dan menerima status sembarang — analisis kode + probe sebagian

`src/api/suppliers.rs:183` tidak membatasi enum status. Daftar `evidence_ids` diverifikasi tanpa memastikan bukti milik supplier pada URL. Error verifikasi diabaikan; perubahan tidak dalam satu transaksi. Tanpa payload seluruh bukti supplier ditandai verified, tetapi payload status saja tidak memverifikasi evidence: hasil berbeda antara dua bentuk permintaan.

Probe terpisah: verifikasi supplier ID yang tidak ada dengan status sembarang tetap HTTP 200 (`A11`).

Perbaikan: enum tervalidasi, cek kepemilikan bukti, pisahkan verifikasi perusahaan dan klaim, transaksi dan rows-affected yang diperiksa.

### A11. Verifikasi supplier tidak ada tetap dilaporkan berhasil — terbukti

`src/api/suppliers.rs:218` mengubah kegagalan fetch menjadi `None`, kemudian mengembalikan sukses. Probe `/suppliers/999999/verify` menghasilkan 200.

Perbaikan: cek keberadaan supplier sebelum mutasi dan kembalikan 404; jangan menelan error database.

### A12. Akun dinonaktifkan dan token setelah logout masih diterima — terbukti

`src/auth/middleware.rs:70` hanya memeriksa signature/expiry token, tanpa status pengguna saat ini atau versi sesi. Logout (`src/api/auth.rs:153`) hanya menghapus cookie. Probe menonaktifkan akun, memanggil logout, lalu memakai bearer lama untuk `/auth/me`: tetap 200.

Perbaikan: mekanisme pencabutan sesi/token, cek is_active dan role terbaru. Cookie belum memakai `Secure`; token juga disalin ke localStorage, yang memperbesar dampak A01.

### A13. Data lokasi lama yang salah tidak diperbarui — analisis kode

`src/database/repositories/suppliers.rs:24` memakai `coalesce(country_code, ?)` dan pola sama untuk alamat/kontak. Data lama non-null selalu menang terhadap temuan baru. Deduplikasi berdasarkan nama bisa langsung return tanpa enrichment.

Dampak: perbaikan resolver tidak otomatis memperbaiki data yang sudah tersimpan. Vendor bisa hilang dari hasil karena alamat lama tetap salah.

Perbaikan: simpan provenance dan waktu/keyakinan per field, mekanisme koreksi serta tinjauan data lama; lindungi hasil koreksi manusia dari overwrite otomatis.

### A14. Satu domain dianggap satu perusahaan — analisis kode

`src/database/repositories/suppliers.rs:12` menggunakan domain sebagai identitas utama. Pada direktori/marketplace yang berisi banyak seller, beberapa perusahaan bisa tergabung ke entitas pertama. Nama perusahaan umum juga dapat bentrok antarnegara.

Perbaikan: bedakan platform sumber dari identitas seller; gunakan URL profil seller dan identitas perusahaan pendukung.

### A15. Job tidak punya batas concurrency global dan panic dapat meninggalkan status running — analisis kode

`src/workers/discovery.rs:80` men-spawn setiap job yang diambil tanpa semaphore job global. Semaphore di `:471` hanya berlaku per batch/job. `tokio::spawn` tidak dipantau; panic tidak melewati jalur `Result::Err`. `stopping` juga tidak dibersihkan oleh startup cleanup yang hanya memilih `running`.

Perbaikan: antrean dengan concurrency global, monitoring join/panic, dan pemulihan seluruh status aktif. Hindari mengklaim antrean melebihi kapasitas.

## Prioritas 2 — kelengkapan hasil, beban dan UX

### A16. Buffer respons tidak dibatasi saat download — analisis kode

`src/services/crawler.rs:79` membaca seluruh `resp.bytes()` sebelum memeriksa ukuran. Halaman/dekompresi besar tetap dapat menghabiskan memori. `crawler_request_delay_ms` tersedia di config tetapi tidak dipakai oleh worker/crawler aktif.

Perbaikan: baca per chunk dan hentikan saat batas terlampaui; terapkan batas global/per-host serta jeda yang benar.

### A17. Heuristik lokasi masih bisa melewatkan atau membuang vendor sah — analisis kode

`src/services/location.rs:124` bergantung pada daftar negara/kota terbatas. Negara di luar daftar bisa tidak dikenali. Pencocokan seluruh field alamat sebagai satu negara tidak memodelkan banyak kantor/cabang. Domain bernegara/platform bisa diblokir sebelum alamat cabang lokal diperiksa (`:598`). Nomor telepon asing langsung bertentangan dengan kantor lokal (`:701`), meskipun bisa berupa nomor layanan regional.

`contact_location_text` (`:692`) memilih baris yang mengandung kata “alamat/address”, tetapi crawler menggabungkan seluruh body menjadi satu baris (`src/services/crawler.rs:151`). Akibatnya pemisahan konteks kontak dari daftar tujuan kirim belum andal.

Perbaikan: ekstraksi blok alamat terstruktur per cabang, negara ISO lengkap, konflik masuk status “perlu cek”, dan jelaskan alasan kandidat dikeluarkan. Lokasi belum dapat dijamin 100% akurat.

### A18. Penambahan query belum menjamin keragaman — analisis kode

`src/services/gemini.rs:533` menambahkan sinonim setelah query lain, lalu truncate di `:539`; sinonim dapat terpotong. `src/services/location.rs:535` mengutamakan negara pertama dan petunjuk subregion pertama. Opsi berisi beberapa kota belum memperoleh porsi pencarian seimbang.

Perbaikan: alokasikan kuota per kota/kelompok query, deduplikasi sesudah penerapan region, dan prioritaskan istilah alternatif sebelum variasi generik.

### A19. Polling job lama bisa menimpa UI job baru — analisis kode

`frontend/js/app.js:604` memperbarui seluruh status tanpa memeriksa apakah respons masih untuk `currentJobId`. Interval 2 detik dapat tumpang tindih. Guard baru hanya ada pada results. Respons job lama berstatus selesai juga bisa menghentikan interval job baru.

Perbaikan: AbortController/generation ID untuk seluruh request, polling berantai setelah respons selesai, dan abaikan semua respons usang.

### A20. Direktori hanya mencari 100 supplier pertama — analisis kode

`frontend/js/app.js:925` selalu meminta `limit=100`, lalu filter keyword di browser. Supplier ke-101 dan seterusnya tidak dapat ditemukan di direktori lewat keyword meskipun ada di database. API mendukung offset tetapi UI belum memakainya.

Perbaikan: pencarian server-side dan pagination dengan jumlah total. Jangan menampilkan nol hasil sebagai bukti supplier tidak tersimpan.

### A21. Detail supplier/RFQ dapat mengambil produk di luar kebutuhan aktif — analisis kode

`frontend/js/app.js:1239` mengambil seluruh offers supplier. `renderRfqPanel`/`buildRfqDraft` memakai konteks job atau offer pertama. Di halaman daftar supplier tidak ada pemilih kebutuhan atau offer yang akan diminta. Tabel pencarian sudah menyaring offers, tetapi drawer belum mengikuti penyaringan itu.

Perbaikan: buka drawer dengan konteks job/product, sediakan pemilih barang dan tampilkan referensi PR yang akan digunakan.

### A22. Seleksi/quotation bisa kehilangan perubahan pengguna — analisis kode

`src/api/purchasing.rs` menyimpan snapshot seluruh formulir melalui upsert tanpa versi/optimistic locking; edit terakhir menimpa data yang disimpan setelah formulir pertama dibuka. `frontend/js/purchasing.js:25` melewatkan reload jika ada load lain berjalan; refresh setelah save bisa dilewati dan tampilan tidak selalu mencerminkan snapshot terakhir.

Perbaikan: version/ETag dan konflik eksplisit; antrekan refresh setelah save; peringatan formulir kotor sebelum mengganti supplier/job atau menutup.

### A23. Statistik/rank dan error dapat menyesatkan — analisis kode

`src/api/dashboard.rs` memakai statistik job global tetapi riwayat job per-user; error database diubah menjadi angka 0/array kosong. Filtering hasil saat baca (`src/database/repositories/search_jobs.rs`) belum menghitung ulang nomor peringkat/count tersimpan, sehingga jumlah kandidat bisa berbeda dari yang tampil. “Putaran” dinaikkan per request pencarian, bukan tahap putaran discovery.

Perbaikan: definisikan cakupan statistik, kembalikan error yang terlihat, dan hitung count/rank berdasarkan hasil yang benar-benar ditampilkan.

## Fitur yang belum lengkap (bukan semuanya bug)

1. Satu kebutuhan/PR berisi banyak item; beberapa pencarian dengan PR sama belum tergabung.
2. Lampiran quotation, datasheet, dokumen legal/vendor dan masa berlaku dokumen.
3. PIC belum berupa relasi akun yang dapat ditugasi; reminder follow-up belum otomatis.
4. Quotation multi-revisi/multi-item, riwayat negosiasi, diskon, konversi kurs dan perhitungan biaya landed cost.
5. Approval pemilihan vendor, pemisahan peran, persetujuan budget, PO serta integrasi ERP.
6. Ekspor khusus shortlist/perbandingan quotation; ekspor saat ini adalah hasil riset web.
7. Pengelolaan pengguna melalui UI, reset password dan pengakhiran sesi aktif.
8. Alur koreksi/import supplier dan produk oleh purchasing, termasuk supplier yang datanya dimiliki di luar aplikasi.
9. Pencarian PDF/katalog, OCR, dan situs berbasis JavaScript; crawler aktif hanya HTML.
10. Dashboard follow-up, quotation kedaluwarsa, pekerjaan per PIC, dan alasan penolakan.
11. Monitoring kualitas pencarian memakai dataset vendor acuan dan uji browser otomatis.
